# AuditLens 政府 PoC 可用差距评估

日期：2026-05-22

## 1. 评估范围

本评估面向 AuditLens 在政府财政监督场景中的交付可用性，重点判断以下三类状态：

- 公网样板环境是否可用于汇报和演示
- 政府 PoC 环境是否可用于单租户试点交付
- 正式政府生产环境是否具备上线条件

本评估基于以下现有材料与代码现状整理：

- `README.md`
- `docs/GOVERNMENT_POC_PACKAGE.md`
- `docs/POC_ACCEPTANCE_CHECKLIST.md`
- `docs/STATUS.md`
- `docs/FUTURE_IMPROVEMENTS.md`
- `config/runtime.poc.json`
- `src/auth/mod.rs`

## 2. 总体结论

当前系统已经超过纯演示原型，具备政府财政监督工作台的核心骨架，可以支撑脱敏样例优先、受控真实小样本参与的政府 PoC 试点。

综合判断如下：

- 公网样板可用性：高
- 政府 PoC 可用性：中
- 政府正式生产可用性：低到中

一句话判断：

> 适合用于政府客户汇报和单租户 PoC 试点，适合脱敏样例和受控真实小样本；暂不建议直接承接大范围真实业务数据或按正式生产系统口径宣称上线。

## 3. 已具备能力

当前仓库已经明确了政府场景下的产品定位、部署边界和主流程能力，主要包括：

- 明确区分公网样板环境与政府 PoC 环境
- 具备租户、组织与角色账户体系
- 具备财政监督主线任务流
- 支持受控数据源模板和白名单表接入
- 支持按部署策略启停 AI
- 支持 PDF 标准报告和密封导出包
- 支持审计留痕与整改闭环
- 支持 PoC 线索收集入口

从现有状态文档看，以下能力也已经完成过验证：

- `cargo test`
- Node 侧脚本和语法检查
- 全流程 smoke 测试
- `poc/public` profile 切换
- 密封包校验
- 平台数据库备份恢复演练

## 4. 主要差距概览

当前差距主要集中在以下五类：

1. 敏感配置与密钥管理仍偏本地文件化
2. 真实数据边界更多依赖流程约定，硬约束不足
3. 审计证据追溯和规则解释尚未完全产品化闭环
4. 真实政府协同流程相关角色已在代码生长，但交付口径尚未统一
5. 运维观测、日志成熟度、重复部署恢复能力仍需加强

## 6. 建议实施顺序

建议先做最影响政府 PoC 交付可信度的事项，再做增强体验和长期工程化事项。

### 第一阶段：PoC 安全可控上线

优先完成以下事项：

- 敏感配置与密钥管理
- 真实数据边界硬约束
- 审计证据追溯
- 安全审计留痕补强

目标：

- 客户环境可以安全部署
- 公网样板与 PoC 数据边界清楚
- 审计结论能够追溯来源
- 关键操作具备可复核留痕

### 第二阶段：结论可解释、流程可闭环

优先完成以下事项：

- 规则解释与误报控制
- 角色模型与交付口径统一
- 整改闭环增强
- 报告与密封包增强

目标：

- 用户可以理解风险结论依据
- 多角色协同流程不再依赖口头补充
- 整改、复核、导出能够形成闭环

### 第三阶段：产品化与长期维护

优先完成以下事项：

- 运维可观测性
- 连接器接入可信度
- 后端拆分降复杂度
- 前端产品化整理
- 回归与 CI
- 生产化部署基线

目标：

- 降低交付回退风险
- 提高排障效率
- 支撑多轮 PoC 与后续产品化迭代

## 7. 建议里程碑

- 里程碑 A：PoC 安全可控上线
- 里程碑 B：结论可解释、证据可追溯
- 里程碑 C：整改闭环与运维成熟度补齐

## 8. 工期判断

按当前整改表粗略估算：

- 最小可交付补齐包：2-3 周
- 相对稳妥的 PoC 强化版：4-6 周

该估算默认前提如下：

- 以现有架构为基础补强，不进行大规模重构
- 以单租户政府 PoC 为目标，不同时推进正式生产多租户要求
- 以现有规则和财政监督场景为主，不额外扩张新的业务条线

## 9. 结论建议

当前最适合的产品口径是：

> 可用于政府客户汇报和单租户 PoC 试点，适合脱敏样例与受控真实小样本；在完成 P0 补齐前，不建议直接承接大范围真实业务数据。

建议将本文件作为后续 PoC 排期、里程碑沟通和验收对齐的基础文档，在每轮整改完成后同步更新优先级、状态和完成日期。
