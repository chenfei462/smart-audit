# AuditLens 政府 PoC 可用差距评估汇报摘要

日期：2026-05-22

## 一、结论摘要

AuditLens 当前已经具备政府财政监督场景下的核心产品骨架，已经不是单纯的演示原型。

现阶段更准确的产品口径是：

> 可用于政府客户汇报和单租户 PoC 试点，适合脱敏样例与受控真实小样本；暂不建议直接承接大范围真实业务数据或按正式生产系统口径宣称上线。

当前可用性判断如下：

- 公网样板可用性：高
- 政府 PoC 可用性：中
- 正式政府生产可用性：低到中

## 二、为什么现在可以做 PoC

当前仓库已经具备以下关键基础：

- 明确区分公网样板环境与政府 PoC 环境
- 具备租户、组织与角色账户体系
- 具备财政监督主线任务流
- 支持受控数据源模板与白名单表接入
- 支持按部署策略启停 AI
- 支持 PDF 标准报告与密封导出包
- 支持审计留痕与整改闭环
- 已完成一轮较完整的测试、备份恢复演练与 profile 切换验证

这意味着系统已经具备进入客户试点的基本条件，但还没有完成正式生产级别的硬化。

## 三、当前最核心的五类差距

### 1. 敏感配置与密钥管理仍偏本地文件化

当前 PoC profile 已经具备策略开关，但敏感配置仍然较依赖本地 JSON 文件管理。对于政府环境，这会影响密钥管控、部署规范性和交付可信度。

### 2. 真实数据边界更多依赖流程约定

现有文档已经明确公网样板不能承载真实政府业务数据，但从系统机制上看，还需要进一步补强“禁止真实数据进入样板环境”的硬约束。

### 3. 证据追溯与规则解释还不够完整

系统已经能识别风险、生成报告，但还需要进一步做到：

- 结论可以反查数据来源
- 导入批次、解析版本、字段映射版本可见
- 风险命中原因能用业务语言解释

这部分直接决定政府用户是否信任结论。

### 4. 真实协同角色已出现，但交付口径尚未统一

代码里已经出现 `department_reviewer`、`supervisor`、`rectification_user` 等更贴近真实流程的角色，但文档、后台展示和验收口径还没有完全同步。

### 5. 运维成熟度仍需加强

当前运维能力已覆盖健康检查、备份恢复、日志归档等基础动作，但距离正式政务环境所要求的分项健康、结构化排障、可重复恢复，还有一段距离。

## 四、建议优先级

### P0：真实 PoC 前优先补齐

- 敏感配置与密钥管理
- 真实数据边界硬约束
- 审计证据追溯
- 规则解释与误报控制
- 高风险操作审计留痕补强

### P1：提升交付质量

- 角色模型与交付口径统一
- 整改闭环增强
- 报告与密封包增强
- 运维可观测性
- 连接器接入可信度

### P2：长期产品化能力

- 后端拆分与复杂度治理
- 前端产品化整理
- 回归测试与 CI
- 生产化部署基线

## 五、建议实施顺序

### 阶段 A：PoC 安全可控上线

目标是先把环境边界、密钥管理、审计留痕和基础合规性补齐，使系统在政府 PoC 场景下“可控可交付”。

### 阶段 B：结论可信、流程闭环

目标是补齐证据追溯、规则解释、角色口径和整改闭环，使客户能够理解并接受系统结论。

### 阶段 C：运维成熟与长期维护

目标是进一步提升可观测性、回归能力和重复部署能力，为后续多轮 PoC 和产品化打基础。

## 六、预估工期

按照当前整改范围粗略估算：

- 最小可交付补齐包：2-3 周
- 相对稳妥的 PoC 强化版：4-6 周

该估算默认以下前提：

- 以现有架构为基础补强
- 不同步推进大规模结构重构
- 目标是单租户政府 PoC，不是正式生产全量上线

## 七、建议对外口径

建议对客户或内部汇报统一使用以下口径：

> AuditLens 已具备政府财政监督场景下的 PoC 试点能力，可支持脱敏样例和受控真实小样本的单租户验证；当前阶段重点是补齐安全、证据追溯、规则解释和运维可控性，以达到更稳妥的政府 PoC 交付标准。
