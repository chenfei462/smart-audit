# AuditLens 后续改进清单

更新时间：2026-04-27

本文档基于当前项目目录、`README.md`、`docs/` 文档、`src/` 与 `static/` 代码结构整理，用于记录后续产品化、PoC 交付和真实数据接入前仍建议推进的改进项。

## 当前状态概览

AuditLens 已具备政府财政监督工作台的核心骨架：租户与角色权限、财政监督任务流、采购 / 预算 / 国库支付 / 会计凭证等多类型导入、规则识别、AI 辅助解读开关、PDF 与密封导出、整改闭环、审计留痕以及公网样板 / 私有 PoC 两类部署策略。

后续重点不应只继续堆功能，而应优先补齐真实 PoC 交付所需的安全、数据可信、运维可控、规则可解释和测试保障。

## P0：真实 PoC 前必须优先补齐

### 1. 安全与合规加固

- 将生产 / PoC 环境中的敏感配置从本地 JSON 文件逐步迁移到更受控的密钥管理方式，至少覆盖会话密钥、AI Key、OCR / ASR Key、连接器凭据。
- 为登录、用户创建、密码重置、AI 配置、连接器配置、导出包生成等高风险操作补齐更细粒度审计日志。
- 明确审计日志保留周期、导出格式、备份策略和篡改检测方式。
- 增加登录失败限制、弱密码拦截、会话过期策略、管理员重置密码后的首次登录改密机制。
- 对公网样板环境增加更硬的保护：禁止真实数据上传、禁止敏感导出、样例数据与真实 PoC 数据隔离。

验收标准：

- PoC 部署文档中能清楚说明密钥、账号、日志、备份、数据边界的处理方式。
- 管理后台能追溯关键操作是谁在什么时间对什么对象做了什么变更。

### 2. 数据接入可信度

- 对导入模板建立版本号和字段映射版本，避免后续模板变化导致旧数据无法复现。
- 在批量导入、连接器导入、公告抓取导入中保存原始来源、采集时间、解析器版本、字段映射版本和数据校验摘要。
- 为采购公告抓取增加失败重试、来源页面快照、附件哈希和解析质量提示。
- 数据库白名单模板需要补充连接预检、字段预览、权限失败提示和只读查询约束说明。
- 官方公开数据样本继续沉淀到 `docs/real-integration/`，把每个样本的业务用途、官方 URL、本地文件和验证结论写清楚。

验收标准：

- 任一审计结论都能反查到原始数据来源、导入批次、解析版本和关键字段。
- 对外演示时能解释“这条风险为什么被识别，以及证据来自哪里”。

### 3. 规则解释与误报控制

- 为采购、预算、支付、凭证勾稽规则建立统一的规则说明字段：规则目的、命中条件、风险等级、适用场景、建议处置。
- 将关键阈值从代码常量逐步迁移到受控配置，并记录配置版本。
- 对 `exact`、`evidence_auto`、`evidence_candidate` 等关联模式建立更明确的人工复核流程，避免候选关系被误当作确定关系。
- 增加误报标记、误报原因、规则调优建议和规则命中回溯功能。
- 对真实 PoC 样本沉淀一组“应命中 / 不应命中”的回归用例。

验收标准：

- 审计人员可以在页面上看到规则命中的业务解释，而不是只看到技术字段。
- 规则调整后可以通过固定样本验证没有破坏既有场景。

## P1：提升交付质量和可运维性

### 4. 整改闭环增强

- 完善案件 SLA：自动计算截止时间、超期提醒、延期申请、延期审批和催办记录。
- 将整改附件、回执、复核意见、处理结论统一纳入案件时间线。
- 增加按责任处室、整改单位、责任人、风险等级、超期状态统计的工作台视图。
- 支持批量分派、批量提醒、批量导出整改台账。
- 明确 `admin`、`auditor`、`viewer` 之外是否需要“被整改单位用户”或“复核用户”角色。

验收标准：

- 一个问题从识别、分派、整改、复核到关闭的全过程能在系统内闭环。
- 可导出满足汇报和督办使用的整改台账。

### 5. 报告与密封导出增强

- PDF 报告增加模板版本、生成时间、数据批次、规则配置版本和导出人信息。
- 密封导出包增加 manifest、文件哈希、导出摘要和校验说明。
- 报告中明确区分确定性结论、候选风险、AI 辅助解释和人工复核意见。
- 增加报告附录：数据来源、规则清单、异常明细、整改状态、证据附件索引。
- 为不同场景准备报告模板：领导汇报版、审计工作底稿版、整改督办版。

验收标准：

- 报告可以脱离系统单独说明结论来源和生成口径。
- 导出包可被第三方复核其完整性。

### 6. AI、OCR、ASR 可控使用

- 继续保持政府 PoC 默认 `aiEnabled=false`，仅在明确批准后启用。
- AI 调用前增加敏感字段脱敏或字段白名单机制。
- 保存 AI 请求摘要、模型配置、返回时间、使用人和结果版本，但避免保存不必要的敏感原文。
- 在界面中明确标识 AI 内容是辅助解释，不作为自动定性依据。
- OCR / ASR 增加任务队列、重试、识别置信度、人工修正和修正留痕。

验收标准：

- AI 关闭时，核心审计、导入、规则、报告、整改流程仍完整可用。
- AI 开启时，能说明数据边界、调用记录和人工复核责任。

## P2：工程化和长期维护

### 7. 后端结构拆分

- `src/web/mod.rs`、`src/platform/v2_store.rs` 等文件已经较大，后续建议按领域拆分为路由、请求响应模型、服务层、存储层和测试模块。
- 将导入、案件、整改、自动化、连接器、报告、用户管理等 API 分组维护，降低单文件变更冲突。
- 为存储层补充数据库迁移版本管理，避免直接依赖启动时隐式修表。
- 逐步抽出领域模型，减少 Web 层直接拼装复杂业务对象。

验收标准：

- 新增一个业务模块时不需要继续扩大单个超大文件。
- 数据结构变更有迁移记录和回滚说明。

### 8. 前端产品化

- 将 `static/index.html` 和 `static/app/*.js` 中的大块页面逻辑拆成更清晰的视图模块和可复用控件。
- 统一表单校验、错误提示、空状态、加载状态、权限不可用状态和成功反馈。
- 增强复杂表格的筛选、排序、分页、列显隐和导出能力。
- 为核心页面补充键盘可用性、响应式布局和较小屏幕下的可读性检查。
- 对重要流程增加前端端到端测试，例如登录、导入、查看结果、导出报告、案件流转。

验收标准：

- 演示时用户不需要依赖口头说明就能完成主流程。
- 页面错误能给出可操作的原因和下一步建议。

### 9. 测试与持续集成

- 在现有 Rust 单元测试基础上补充 API 集成测试，覆盖权限、导入、导出、案件、整改、连接器等主流程。
- 建立固定真实样本和脱敏样本的回归测试集。
- 增加前端 `node --check`、基础 E2E、格式检查和构建检查。
- 建立 CI 流程，至少运行 `cargo test`、前端语法检查和关键样本导入回归。
- 对报告和密封包增加快照或结构化校验，防止导出格式被无意破坏。

验收标准：

- 每次交付前可以用一组固定命令确认主流程没有回退。
- 关键规则和真实样本关联逻辑有稳定回归覆盖。

### 10. 运维观测与部署成熟度

- 健康检查从单点 `/api/health` 扩展为应用、数据库、配置、OCR / ASR、AI、连接器的分项状态。
- 增加结构化日志、错误码、请求 ID 和关键指标统计。
- 补充备份恢复演练脚本，验证 `data/platform.db` 和 `platformDataDir` 能在新环境恢复。
- 为公网样板、内网 PoC、正式私有化部署分别维护配置基线。
- 明确 Windows 本地运行、Linux 服务化部署、反向代理、HTTPS、日志轮转的操作步骤。

验收标准：

- 出现导入失败、登录失败、导出失败、AI 失败时，运维人员能快速定位原因。
- PoC 环境可以被重复部署和恢复，而不是依赖单机手工状态。

## 建议路线图

| 阶段 | 目标 | 建议内容 |
| --- | --- | --- |
| 近期 | 真实 PoC 可控上线 | 安全配置、审计日志、数据来源追溯、规则解释、PoC 样本回归 |
| 中期 | 提升交付效率 | 整改闭环、报告模板、连接器预检、前端流程体验、运维脚本 |
| 长期 | 产品化维护 | 后端模块拆分、数据库迁移、CI、E2E、可观测性、多环境配置基线 |

## 暂不建议优先投入的方向

- 在没有真实 PoC 数据反馈前，不建议过早扩大 AI 自动判断范围。
- 在规则解释和误报控制未稳定前，不建议把候选关联直接升级为自动定性结论。
- 在数据来源追溯未补齐前，不建议把公网抓取结果作为强审计证据单独使用。
- 在部署、备份、日志、权限未固化前，不建议承接大范围真实数据。
